# 3. Trust model and credentials

Status: spec, not built.

## Principle

**Launch holds the admin credentials. Apps get derived, narrowly scoped credentials, and
sandboxes get almost nothing.** A leak from one app must not reach another app, and a leak from a
coding session must not reach anything beyond that app's repo.

## Admin credentials (Launch only)

Launch stores these as its own Worker secrets, set once in the setup wizard:

| Credential | Scope | Used for |
|---|---|---|
| Cloudflare account-owned API token | Account: Workers Scripts, KV, Queues, R2, Hyperdrive, Workflows (Edit); Zone DNS + Workers Routes (Edit) on the apps zone; **Account API Tokens: Edit** (to mint per-app tokens) | Creating resources, custom domains, Worker secrets, per-app tokens |
| Neon organization API key | The company's Neon org | A project per app, branches, roles, project-scoped keys |
| Resend full-access API key | The company's Resend account | A sending domain per app, plus a sending key per app |
| GitHub App (app id + private key), installed on the company org | Administration, Contents, Pull requests, Actions, Environments, Secrets, Deployments (write); `deployment_protection_rule` webhooks | Repo creation, commits, environment secrets, production gating, short-lived tokens |
| Anthropic API key (or a Bedrock/Vertex credential) | Sessions | Coding sessions |
| Upstream IdP client (Google or Microsoft) | Company directory | Signing people in to Launch ([05](05-identity-sso.md)) |
| OIDC signing keys | — | Signing id tokens for apps |

The first Cloudflare token has to be created in the dashboard by a Super Administrator. The
Cloudflare API can't bootstrap its own first token. The wizard walks the admin through this step
and checks the permissions it was given.

## Derived credentials (per app)

| For | Credential | Scope | Lives in |
|---|---|---|---|
| CI deploys | Cloudflare account token with **per-Worker scoping** (Editor on `<slug>` and `<slug>-staging` only). Granular Worker permissions shipped 2026-09-15 | Its own Workers | GitHub Environment secret `CLOUDFLARE_API_TOKEN` |
| Database | Neon connection string per branch (a dedicated role); optionally a project-scoped Neon API key | Its own project | GitHub Environment secret `DATABASE_URL`; Hyperdrive config |
| Email | Resend `sending_access` key **bound to its own domain** | Sending from `<slug>.apps.example.com` only | Worker secret `RESEND_API_KEY` |
| Sign-in | OIDC client id + secret | Its own redirect URIs | Worker secrets |
| App encryption | `OAUTH_ENCRYPTION_KEY`, generated by Launch | Its own sealed data | Worker secret (write-only; Launch keeps no copy, see below) |
| Granted shared config | Whatever was approved ([09](09-config-and-grants.md)) | Per grant, per environment | Worker secrets / vars |

**Whether Launch keeps copies of what it mints.** For credentials it can mint again (Resend keys,
Neon passwords, Cloudflare tokens, OIDC secrets), Launch keeps only ids and metadata, and rotation
means minting a new one. For values it has no other source for (grant bundles, the app's
encryption key), Launch keeps the value sealed at rest, or else it can't restore it. The app's
encryption key is special: rotating it breaks every value the app has sealed, so Launch treats it
as generated once, is never rotated automatically, and is kept sealed for recovery.

## Sandboxes

A coding session sandbox ([07](07-coding-sessions.md)) receives:

- a GitHub installation token scoped to **one repository**, with `contents` and `pull_requests`
  write. It lasts an hour and is refreshed by the SessionDO, never by the sandbox;
- a model credential. It is proxied, not injected, where possible: the SessionDO forwards model
  calls and meters them. Where the Agent SDK needs a direct key, a per-session key with a budget
  is used;
- **no** Cloudflare, Neon, Resend or grant credentials. Local development in the sandbox runs on
  the template's zero-credential mode.

Egress is allowlisted: Anthropic, GitHub, the npm registry and the template's documented
dependencies. The scaffold sandbox ([06](06-registry-and-pipeline.md)) is stricter: no model
credential at all.

## What the UI shows

For every credential, only **whether it is set**, when it was set or rotated, and by whom. A
value is never returned by any API after it is written. This matches Rocketflare's own
`hasCredential` convention.

## Known gaps

- The Cloudflare API docs don't clearly state the resource-id format for per-Worker token
  policies. It needs a spike.
- A Neon project-scoped key is member-level on one project. Whether apps need a Neon API key at
  all, or only a connection string, is open. The default is connection string only.
- If Launch's own Worker secrets leak, the admin credentials leak with them. The mitigation is
  Cloudflare's account audit log plus rotation; there is no hardware-backed store on Workers.
