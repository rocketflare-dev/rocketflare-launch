# 3. Trust model and credentials

Status: spec, not built.

## Principle

**Launch holds the admin credentials. Apps get derived, narrowly scoped credentials, and
sandboxes get almost nothing.** A leak from one app must not reach another app, and a leak from a
coding session must not reach anything beyond that app's repo.

## Admin credentials (Launch only)

Launch stores these as its own Worker secrets, set once in the setup wizard:

| Credential | Scope | Used for |
|---|---|---|
| Cloudflare account-owned API token **for the apps account** ([01](01-overview.md)) | Account: Workers (Admin), KV, Queues, R2, Workflows (Edit); Zone DNS + Workers Routes (Edit) on the apps zone | Creating resources, uploading every app's Workers and assets, Worker routes, Worker secrets |
| Neon organization API key | The company's Neon org | A project per app, branches, roles. It can't mint project-scoped keys, which need a personal key (S3) |
| Resend full-access API key | The company's Resend account | The one `notifications.` sending domain, plus a sending key per app |
| GitHub App (app id + private key), installed on the company org | Administration, Contents, Workflows, Pull requests, Actions, Environments, Variables, Deployments (write) | Repo creation, commits, dispatching deploys, short-lived tokens |
| Anthropic API key (or a Bedrock/Vertex credential) | Sessions | Coding sessions |
| Upstream IdP client (Google or Microsoft) | Company directory | Signing people in to Launch ([05](05-identity-sso.md)) |
| OIDC signing keys | — | Signing id tokens for apps |

The first Cloudflare token has to be created in the dashboard by a Super Administrator. The
Cloudflare API can't bootstrap its own first token. The wizard walks the admin through this step
and checks the permissions it was given.

## Derived credentials (per app)

| For | Credential | Scope | Lives in |
|---|---|---|---|
| CI deploys | **None.** The deploy job proves who it is with a GitHub Actions OIDC token (repo, environment, ref) and hands its build to Launch, which deploys it ([08](08-approvals-audit-ship.md)) | — | Nothing stored in GitHub |
| Database | Two roles per branch, each **reset after branching** (a branch inherits its parent's passwords, S3): `app` for the Worker, and `migrator` (the database owner) for migrations | Its own branch | `app`'s pooled URI: Worker secret `DATABASE_URL`. `migrator`: **no stored credential**; Launch resets its password for each approved deploy run once its build has passed the check, hands it over through the OIDC exchange, and resets it again afterwards (S5) |
| Email | Resend `sending_access` key of its own, **bound to the shared `notifications.` domain** | Sending from that domain; a sender address can't be enforced ([04](04-hostnames-and-dns.md#email)) | Worker secret `RESEND_API_KEY` |
| Sign-in | OIDC client id + secret | Its own redirect URIs | Worker secrets |
| App encryption | `OAUTH_ENCRYPTION_KEY`, generated by Launch | Its own sealed data | Worker secret (write-only; Launch keeps no copy, see below) |
| Granted shared config | Whatever was approved ([09](09-config-and-grants.md)) | Per grant, per environment | Worker secrets / vars |

**Whether Launch keeps copies of what it mints.** For credentials it can mint again (Resend keys,
Neon passwords, Cloudflare tokens, OIDC secrets), Launch keeps only ids and metadata, and rotation
means minting a new one. For values it has no other source for (grant bundles, the app's
encryption key), Launch keeps the value sealed at rest, or else it can't restore it. The app's
encryption key is special: rotating it breaks every value the app has sealed, so Launch treats it
as generated once, is never rotated automatically, and is kept sealed for recovery.

## Sandboxes

A coding session sandbox ([07](07-coding-sessions.md)) receives:

- a GitHub installation token scoped to **one repository**, with `contents` and `pull_requests`
  write. It lasts an hour and is refreshed by the SessionDO, never by the sandbox;
- **no model credential.** The sandbox holds a placeholder key. An outbound handler for
  `api.anthropic.com`, running in Launch's Worker outside the sandbox, swaps in the real key and
  meters every call from the response stream ([S7](../spikes/s7-sandbox/RESULT.md));
- a connection string for **its own Neon session branch** only, deleted with the session;
- **no** Cloudflare, Resend or grant credentials. Local development in the sandbox runs on the
  template's zero-credential mode.

Egress is allowlisted (`enableInternet = false`, `allowedHosts`, and **`interceptHttps = true`**,
which is off by default on the stable packages): Anthropic, GitHub, the npm registry and the
template's documented dependencies. A host with an outbound handler must be allowlisted too. The
allowlist covers HTTP(S) only, so **Postgres over TCP can't leave a session**: the database is
reached over Neon's HTTPS/WebSocket driver (spec/02 gap 2). The scaffold sandbox ([06](06-registry-and-pipeline.md)) is stricter: no model
credential at all.

## What the UI shows

For every credential, only **whether it is set**, when it was set or rotated, and by whom. A
value is never returned by any API after it is written. This matches Rocketflare's own
`hasCredential` convention.

## Known gaps

- **Per-Worker tokens don't isolate apps** ([S1](../spikes/s1-worker-token/RESULT.md)). The format
  works (`com.cloudflare.edge.worker.script.<tag>` nested under the account, "Individual Workers
  Editor"), but a token scoped to app A's Workers can deploy A with bindings to **any** resource
  in the account: B's KV, R2, Queues and Worker, or Launch's own Hyperdrive. That is why CI holds
  no Cloudflare token and Launch checks every binding before it deploys. A company that opts an
  app out of Launch deploys can still mint one, with this risk stated.
- Apps get connection strings only, never a Neon API key. The org key can't mint project-scoped
  keys anyway (S3).
- If Launch's own Worker secrets leak, the admin credentials leak with them. The mitigation is
  Cloudflare's account audit log plus rotation; there is no hardware-backed store on Workers.
