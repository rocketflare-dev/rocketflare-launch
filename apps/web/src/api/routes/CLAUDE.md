# API Routes

Hono routers mounted in `src/api/index.ts`. Thin controllers: validate → authorise → query → respond.

## Layout

- `health.ts` — `/api/health`, `/api/ready`. Public.
- `auth/` — public (rate-limited where login-shaped): `session.ts` (`/auth/methods|session|select-tenant|logout` — logout answers `200 { endSessionUrl }` when an OIDC issuer advertises `end_session_endpoint`, else 204), `magic-link.ts` (`/auth/magic-link/request|verify`), `oauth.ts` (ONE generic `/auth/:provider` + `/callback` over `auth/providers` — incl. `oidc`; `?returnUrl=` (or `?redirectTo=`); under `AUTH_OIDC_ONLY` every other provider → `/login?error=oidc_only`), `dev-login.ts` (development only), `providers.ts` (linked identities), `cli.ts` (`/auth/cli?redirect_uri=` loopback key hand-off, D26), `helpers.ts` (`completeLogin`, `safeRedirectPath`). Static routes mount BEFORE the generic `/:provider` router.
- `invite.ts` — public `GET /api/invite/:token`, cookie-required `POST /api/invite/:token/accept` (transactional).
- Behind `authMiddleware` (cookie or Bearer): `me.ts`, `tenant.ts` (current tenant + `/settings`), `tenants.ts` (mine; create — multi only), `members.ts`, `invitations.ts` (+ tenant-free `GET /pending`), `keys.ts`, `notifications.ts`, `activity.ts`, `access-requests.ts` (tenant-free), `files.ts` (D23: `POST /api/files?scope=` multipart `file` → 201 `fileSchema`; `GET /:id` streams from R2 with `Cache-Control: private`, `ETag`/304, `inline` for `INLINE_MIME_TYPES` (the avatar images **plus `application/pdf`**) else `attachment`; a PDF additionally sets `c.set('embeddable', true)` BEFORE the 304 early return so `securityHeaders` answers `SAMEORIGIN` + `frame-ancestors 'self'` and the document viewer can frame it — only a route that has proved the content type may set that flag; `DELETE /:id` uploader-or-`delete File`; `avatars` scope writes `users.avatarUrl`; 503 `storage_not_configured` without `FILES`).
- AI (D17/D18/D32), all behind `authMiddleware`; logic in `services/ai/*`, `services/agents/**`, `services/prompts.ts` — routes never import an SDK or read `ai_configs`:
  - `ai-config.ts` → `/api/ai/config`: `GET /` (rows as `aiConfigSchema`, `hasCredential` never the key; `read AiConfig`), `GET /providers` (the `PROVIDERS` catalog + `defaultMaxOutputTokens` — **no shared schema**, the UI parses it permissively), `GET /readiness` (`readiness()` — what the resolvers WOULD pick, no 503), `POST /test` (`testConfig` on a saved `configId` or an inline candidate; rate-limited 10/min/IP; `manage AiConfig`), `POST /` (upsert on `(tenant, scope, label)`; omitted `apiKey` keeps the stored one, a provider change without a key drops it; `isDefault` swaps inside one transaction, the first row in a scope is default; 201 create / 200 update), `DELETE /:id` (204).
  - `ai-prompts.ts` → `/api/ai/prompts`: `GET /`, `GET /:key` (member read), `PUT /:key` / `DELETE /:key` (`manage Prompt`; unknown key → 404 `prompt_not_found`; the registry is code).
  - `ai-usage.ts` → `GET /api/ai/usage/summary?from&to` (`summarizeUsage`, default 30 days, `from >= to` → 400 `invalid_range`; `manage AiConfig`).
  - `ai-agent-models.ts` → `/api/ai/agent-models`: `GET /` (every registry prompt key + assignment + the `effective` pick via `planChat` — the same function `resolveChat` uses), `PUT /:promptKey` (pin `aiConfigId` — tenant-scoped, foreign id → 404 `ai_config_not_found` — and/or `model`), `DELETE /:promptKey` (revert, idempotent 204); writes `manage AiConfig`.
  - `ai-documents.ts` → `/api/ai/documents`: `POST /ingest` (`ingestText` with `c.env.JOBS_QUEUE`; 201 with `status` `indexed` or `pending` when queued; `create Document`), `GET /` (paginated, `?status=`), `POST /search` (`searchChunks` hybrid RRF), `GET /:id`, `GET /:id/content?offset=&maxChars=` (one character window over `documents.content`, sliced in Postgres; 409 `document_not_converted` / `document_conversion_failed` when there is no text), `GET /:id/passages` (paginated, columns named so `embedding` cannot leak), `GET /:id/card`, `DELETE /:id` (owner or `delete Document`; chunks cascade). All three reads go through `services/ai/document-content.ts`, the same service `get_document` uses. Vectors never leave the server, and the text only ever leaves one window at a time.
  - `chat.ts` → `/api/chat`: `GET|POST /conversations` (POST resolves the client FIRST → 503 `ai_not_configured` before any row; freezes `provider`/`model`), `GET|DELETE /conversations/:id`, `POST /conversations/:id/messages` — a thin wrapper over `services/ai/chat-turn.ts`: `prepareChatTurn` runs everything that can fail as JSON (resolve, `resolvePrompt('chat')`, last 40 turns, user-message insert), then `streamChatTurn` streams **AG-UI** (`RUN_STARTED → CUSTOM kit.chat.ids → STATE_SNAPSHOT → per-turn TEXT_MESSAGE_*/TOOL_CALL_* → CUSTOM kit.usage → RUN_FINISHED`, or `RUN_ERROR`; a cancelled run emits nothing). Frames are `data:` only — no `event:` line — or protobuf when the client negotiates it. Knowledge tools are on unless `CHAT_KNOWLEDGE_TOOLS=false`, built from the STREAM's client; writes inside the stream use **`streamDatabase(c)`** and are awaited, then `recordUsage`, then `tracer.flush()`. Ownership = `userId` filter on every query (others' threads 404, admins included).
  - `agui.ts` → `POST /api/agui/run`: the AG-UI `RunAgentInput` endpoint, mounted BESIDE `/api/chat` (the mount list is the enumerable auth surface). Validates `kitRunAgentInputSchema`, `update Conversation`, then reconciles — **the server is the transcript, the client supplies only the tail**: an unknown `threadId` is adopted as a conversation (after `resolveChat`, so a 503 precedes any row; one belonging to someone else → 404 `agui_thread_not_found`), the LAST message is the new user turn and earlier ones are ignored, a replayed UUID message id is not re-inserted, and `MESSAGES_SNAPSHOT` reports the server's transcript in-band. Non-empty `tools[]` → 400 `agui_client_tools_unsupported` (refused, never ignored). Then the SAME `streamChatTurn` the chat route calls.
  - `agents.ts` → `/api/agents`: `GET /` (registry), `GET /runs` (paginated; members their own, `isAdminLevel` all), `POST /runs` (`enqueueRun` → 202 + row, `deduplicated: true` when an active exclusive run exists; `?strict=1` → 409 `agent_run_active`; no binding → 503 `agent_runs_not_configured`), `GET /runs/:id` (`reconcileRun` against `instance.status()` then row + `events`), `GET /runs/:id/agui` (the same run projected into AG-UI, plain JSON, with `lastSeq` as the tail cursor), `GET /runs/:id/agui/stream` (issue #7 — the LIVE tail, `services/agents/run-stream.ts`; GET so a bare `EventSource` works, `?afterSeq=` beating `Last-Event-ID`; everything that can fail is JSON above the stream, **`reconcileRun` runs exactly once there and never in the loop**, and a read-stream failure emits **no `RUN_ERROR`** — closing with no terminal event means *reconnect*), `POST /runs/:id/cancel` (`requestCancel`, cooperative). Human-in-the-loop (issue #17): `POST /runs/:id/interrupts/:interruptId` answers ONE ask — visible run → `canAnswer` (`update AgentRun` + the agent's `approvers`, 403) → the ask → `interruptPayloadSchema(spec)` (400; an `editedInput` also re-checked against the tool's stored schema) → `resolveInterrupt`'s single compare-and-set (null → 409 `interrupt_not_pending`) → an `interrupt.resolved` row → **only when nothing is still pending**, `resumeRun` THEN `nudgeOrRestartInstance` (*the answer is the transition*); `POST /runs/:id/steering` appends a note through `appendEventAtomic` (409 on a settled run); `GET /interrupts?status=` is the inbox (own runs for a member, the tenant's for admin+, `canAnswer` per item). `GET /runs/:id` and `/agui` are `requireRun` (lookup + the ownership 404) then `settleOnRead` (`reconcileRun` **and** `expireParkedRun`) — in that order, with the log read BETWEEN them so its newest `at` goes in as `lastEventAt` and a live run costs **no** Workflow subrequest; they carry `interrupts[]` / `artifacts[]`, and `?events=0` is the bare row (no log in hand, so it reconciles unconditionally, as does the stream). `loadRun` is the two halves in one call. The route never runs the agent.
- `feedback.ts` (D33, `/api/feedback`): thumbs on AI answers — `POST /` (`create Feedback`, every member; `services/feedback.ts` proves the rater can READ the target — own thread only, admins included; own run unless admin-level — and a foreign id is a 404), `DELETE /:target/:targetId` (withdraw your own vote, 204, idempotent), `GET /mine?target=&targetIds=a,b` (your own votes, for the thumbs' state), `GET /` (`read Feedback`, admin+ — the promotion queue, `?rating=up|down&target=`, paginated). A vote is also a zero-length `feedback` span under the answer's trace root.
- `evals.ts` (D33, `/api/evals`): `GET /export?messageId=|runId=` → a draft `EvalCase` (question, earlier turns, retrieved passages, tools called, the observed answer as `expected.output`, the latest feedback) with `containsTenantData: true`. `read Feedback`, admin+; every lookup carries the tenant. The CLI's `evals promote` is the reader.
- `traces.ts` (D32, `/api/traces`): the local AI trace store read back — `GET /` (one row per trace, `?runId|conversationId|since|agent|status`, paginated; status is the ROOT's once recorded, else "any span errored"), `GET /:id` (the trace's spans oldest first, parent-linked; `:id` is a trace id, an agent run id or an assistant message id, resolved in `services/traces.ts` with the tenant on every lookup, so another tenant's id is `404 trace_not_found` like an unknown one). `read Trace` — owner/admin/support only; spans hold other people's prompts, so a member cannot read even their own run's. The CLI's `traces list|show` is the reader.
- `ws.ts` — `GET /ws?tenantId=`, mounted WITHOUT `authMiddleware` (a browser cannot set headers on an upgrade): resolves the cookie via `resolveCookieAuth`, checks membership in the requested tenant, forwards to `NOTIFICATIONS_HUB.idFromName(tenantId)` with `X-Tenant-Id/X-User-Id/X-Session-Id`. Not an upgrade → 426 `upgrade_required`; no cookie → 401; no membership → 403; suspended → 403 `tenant_suspended`.
- `groups.ts` (D29, `/api/groups`): `GET /mine` (any member — their own groups); everything else is `manage Group` — `GET|POST /types`, `PATCH|DELETE /types/:id`, `GET|POST /`, `GET|PATCH|DELETE /:id`, `POST /:id/members { userIds }` (every id must already be a tenant member → 400 `not_a_member`), `DELETE /:id/members/:userId`. A delete that would change who can see content is 409 `group_in_use` with `{ documents, dashboards }` unless `?force=1`, and forcing narrows the affected resources (they keep `visibility: 'groups'` with fewer grants) — it never opens them. Membership changes nudge `entity.changed { entity: 'groups' }` tenant-wide AND `access.changed` to the affected users. `PUT /api/members/:userId/groups` is the same decision taken from the person's side.
- `features.ts` (D30, `/api/features`): `GET /` — the EFFECTIVE flags for the active tenant, any member, answered from `auth.features` so it costs no query and cannot disagree with any other gate. It is what `launch features list` reads, because a Bearer key cannot reach `/api/admin/*`. Administering flags is `admin.ts` (`GET /feature-flags`, `PATCH /feature-flags/:key`, `GET|PUT|DELETE /feature-flags/:key/overrides[/:tenantId]`) behind `globalAdminMiddleware`; `:key` is a registry key, NOT a uuid, so it is validated against `isFeatureName` and an unknown one is a 404. The override sub-routes call `requireMultiTenant` (with one organisation the platform state already IS its answer) and `PATCH` refuses a rollout counted in organisations there. An override change nudges `features.changed` to that tenant; a platform change does not — one Durable Object per tenant makes a fan-out one RPC each, so it lands on the next `GET /auth/session`.
- **Visibility (D29)** on every resource that carries it — the kit's `documents` plus each installed plugin's (D31): `PUT /api/ai/documents/:id/visibility` is the document's OWNER or `manage Document`. Every read path ANDs the resource's predicate (`visibleDocuments(scope)`; a plugin's own comes from its `visibilityResources` entry) onto the tenant predicate, and answers the SAME 404 for a hidden row as for an absent one. `GET /api/files/:id` applies the OWNING DOCUMENT's visibility to a `documents`-scope object.
- Behind `globalAdminMiddleware`: `admin.ts` — the only cross-tenant surface; logic in `services/admin.ts`.
- **Launch (P1, `docs/CONCEPTS.md` §18)**, contracts in `@launch/shared/launch-{apps,oidc,setup,audit}`:
  - `oidc.ts` — PUBLIC, outside `/api`: `wellKnownRouter` (`/.well-known/openid-configuration`, `jwks.json`) and `oidcRouter` (`/oidc/authorize|token|userinfo`, `GET|POST /oidc/logout`). Protocol errors are RFC 6749/OIDC shaped (`{ error, error_description }`), not the kit envelope; an unregistered client or URI gets an HTML page, never a redirect. Logic in `services/oidc/{store,keys,tokens,policy,discovery}.ts`; `store.ts` is the allowlisted pre-tenant lookup.
  - `apps.ts` (`/api/apps`, `authMiddleware`; `read App` / `manage App`): list (with `appsDomain`), `GET /:slug` (with the caller's `viewerCanDeploy`), `POST /import`, `PATCH /:id`, `GET /:id/health`, `POST /:id/health-check`, `GET /:id/operations`, `GET|POST /:id/oidc-client`, `POST …/rotate-secret`, `PATCH …/redirect-uris`. Logic in `services/launch/{apps,import,rocketflare-manifest,health,oidc-clients}.ts`.
  - `app-access.ts` (`/api/app-access`, `authMiddleware`): the request-access page's context and request, and the owners'/admins' policy, grants and decisions.
  - `audit.ts` (`/api/audit`, admin+) over `services/launch/audit.ts`.
  - `setup.ts` (`/api/admin/setup`) and `oidc-admin.ts` (`/api/admin/oidc`: keys, rotate) — mounted BEFORE `/api/admin`, global admins; logic in `services/launch/{setup,credentials,cloudflare,neon,resend,github-app}.ts`.
- **Launch P2 (creating apps, `docs/plans/p2-create-app.md`)**, contracts in `@launch/shared/launch-pipeline`:
  - `ci.ts` — PUBLIC, outside `/api` beside `/oidc`: the GitHub-OIDC surface a CI job calls, with `ciBodyLimit` (64 MB on `POST /ci/deploy/:id/upload`, 1 MB elsewhere). Mounts `ci-deploy.ts` at `/deploy` (the external deployer protocol v1 — slice 2d) and `ci-scaffold.ts` at `/scaffold` (the scaffold job's `token` and `done` — slice 2b). Every handler first `verifyGitHubOidc(bearerToken(…), { audience: cfg.APP_URL })` (401) then `resolveCaller(db, claims, { workflowFile })` (403) from `services/launch/ci/`, and uses only the tenant of the resolved app row.
  - `ci-scaffold.ts` (`/ci/scaffold`, `workflowFile: launch-scaffold.yml`, resolved to the app's production environment): `POST /token` claims the waiting scaffold ticket for the calling run and returns a one-hour installation token scoped to the one repo (`contents` + `workflows` write) with the plan, ONCE (409 `scaffold_token_unavailable` after); `POST /done {commit}` finishes the ticket and sends `SCAFFOLD_FINISHED_EVENT` to the live launch instance (`pipeline/instance.ts`). Logic in `services/launch/scaffold/{service,tickets}.ts`.
  - `ci-deploy.ts` (`/ci/deploy`, `workflowFile: deploy.yml`): the deployer protocol v1 — `POST /start` (staging auto-approved; production claims a "Deploy to production" pre-approval or opens `pending`), `GET /:id`, `POST /:id/upload` (binding check → 403 `{ error, refused }` with NO Neon call; else the version upload and the one-deploy `migratorUrl`), `POST /:id/activate` (100% deployment, schedules, workflows, revoke), `POST /:id/finish` (idempotent; `DEPLOY_FINISHED_EVENT` to the live launch instance). Each call checks the token's run and environment against the ticket (403). Logic in `services/launch/deploy/{gateway,tickets,binding-check,worker-upload,migrator}.ts`.
  - `app-pipeline.ts` (slice 2c: `POST /api/apps` → 202, `GET /:id/pipeline`, `POST /:id/pipeline/retry`, `POST /:id/teardown`) and `app-deploys.ts` (slice 2d: `GET /:id/deploys`, `POST /:id/deploys/:ticketId/decide`, `POST /:id/deploys/production`; deciding and deploying is the app's owners and admins, `mayDeployApp` in `services/launch/apps.ts`, which is also the detail's `viewerCanDeploy`; creating, retrying and archiving are `manage App`) — sub-routers mounted by `apps.ts` with `appsRouter.route('/', …)` BEFORE its `/:slug` routes, under the `/api/apps` mount's `authMiddleware`.
  - Services (slice 2a): `services/launch/ci/{github-oidc,caller}.ts` (the two `/ci` proofs; `caller.ts` is the allow-listed pre-tenant lookup), `services/launch/pipeline/operations.ts` (`runStep` / `skipStep` over `app_operations`), `services/launch/deploy/tickets.ts` (pre-tenant ticket reads; 2d adds the compare-and-set transitions), and the vendor writes on `CloudflareClient`, `NeonClient` (+ `runSql`), `ResendClient` and `github-app.ts`.
- **Launch P3 (coding sessions, `docs/plans/p3-sessions.md`)**, contracts in `@launch/shared/launch-sessions`. Four files, each owned by one slice so they are built in parallel; all stubs from slice 3a (routers with no routes — an unmatched path is the catch-all's JSON 404):
  - `sessions.ts` (`/api/sessions`, 3b: `GET /:id`, `POST /:id/resume`) mounts `session-chat.ts` (3c: `POST /:id/turns`, `/cancel`, `/budget`, `GET /:id/events`, `/agui/stream`) and `session-ship.ts` (3d: `POST /:id/ship`, `/end`, `/preview-grant`, `GET /:id/pr`) FIRST, so a `/:id` route never shadows theirs. Every one resolves the session with `getVisibleSession` (`services/sessions/access.ts`): the creator, the app's owners and admins; anyone else gets the same 404 `session_not_found` as a missing one.
  - `app-sessions.ts` (3b: `POST|GET /api/apps/:id/sessions`) — a sub-router mounted by `apps.ts` with `appsRouter.route('/', …)` BEFORE its `/:slug` routes.
  - `admin-sessions.ts` (3b: `/api/admin/sessions` — list, `POST /drain`, `POST /undrain`), mounted before `/api/admin` behind `globalAdminMiddleware`.
  - NOT a route: the preview gateway (`api/preview/gateway.ts`) — `worker.ts` sends preview HOSTS there before the Hono app.
- An installed PLUGIN's routers are NOT in this directory (D31): they live in
  `src/plugins/<id>/api/` and reach the mount table through `ServerPlugin.mounts`, spread in last.
  The prefix is `/api/<id>`, the optional third element is its `requireFeature` gate, and the file
  layout and rules are identical to everything above — the only difference is that nothing in
  `api/index.ts` names the plugin.
- Guard list, per mount: public — `health`, `/auth/*`, `GET /api/invite/:token`, `/oidc` + `/.well-known` (the issuer), `/ci/*` (GitHub OIDC, P2), and every installed plugin's `publicMounts` under `/api/hooks/<plugin id>` (D34: consent callbacks and webhooks; the handler proves the caller — `verifyState`, a stored secret, a provider signature — before it touches a row, and the config test refuses a public mount anywhere else); `globalAdminMiddleware` — `/api/admin/*`; cookie-resolved — `/ws`; `authMiddleware` — every other `/api/*` and every prefix an installed plugin mounts (D31; the analytics plugin's `/api/analytics`, `/cubejs-api` and `/mcp`). A plugin's own guards are its business and use the same `guardPermission` over its own subjects.
- Logic lives in `services/{auth,tenants,members,invitations,admin,notifications,activity,email,jobs,realtime,storage,prompts}.ts`, `services/ai/*` and `services/agents/**`; routes validate → authorise → call a service → respond. `utils/db/tenant-helpers.ts` `onTenantCreated` is the post-commit tenant hook — the kit contributes none since analytics became a plugin, so it is every installed plugin's hook, each best-effort in its own try/catch and handed the deployment's `features` (a hook that CREATES rows is the sharpest feature door there is). `services/jobs.ts` (`enqueueJob`) and `services/realtime.ts` (`nudge*`) are the only paths to `JOBS_QUEUE` and `NOTIFICATIONS_HUB`; `services/ai/resolve.ts` the only path to `ai_configs` / `agent_models` / the `AI` binding; `services/agents/runs.ts` the only path to `AGENT_RUN_WORKFLOW`. Consumers are in `../queues/`, the DO in `../durable-objects/`, the Workflow class in `../workflows/`.

## Rules

- `createRouter()` from `utils/routes/router.ts` — never `new Hono()` (D13). It gives `c.get('config' | 'db' | 'logger' | 'requestId')` types.
- Request contracts are zod schemas in `packages/shared/src/` (`@launch/shared/<module>`; UI and CLI import them too). Validate with `validate('json' | 'query' | 'param', schema)` from `utils/routes/validate.ts`; a bad input becomes the shared 400 envelope with `code: 'validation_failed'`.
- Read config via `c.get('config')`, never `c.env` (D3). Bindings are passed INTO services from the route, never read inside them: `c.env.JOBS_QUEUE` → `createInvitation(db, cfg, logger, jobs, …)`, `c.env.FILES` → `createR2Storage(...)`; `NOTIFICATIONS_HUB` only ever via the `realtime` that `withAuth` returns.
- Body limits: the global `jsonBodyLimit` (1 MB) skips `/api/files` (`isUploadPath`); `files.ts` mounts `uploadBodyLimit` (`MAX_UPLOAD_BYTES + 64 KB`) on its `POST` and enforces the exact 5 MB per file (413 `payload_too_large`) and the avatar allowlist (415 `unsupported_media_type`) itself. A new upload route must do the same two things — the transport cap is not the per-file limit.
- Throw typed errors from `utils/core/errors.ts` (`NotFoundError`, `ForbiddenError`, ...). Do not hand-roll `c.json({ error }, 4xx)`; `middleware/error-handler.ts` owns the envelope `{ error, statusCode, code?, details? }`.
- Success bodies are bare domain objects (no envelope). Lists use `paginatedResponse(item)` from `@launch/shared/pagination` → `{ items, pagination: { page, pageSize, total, totalPages } }`.
- Auth is applied AT THE MOUNT in `index.ts` (`app.use('/api/x/*', authMiddleware); app.route('/api/x', xRouter)`), never inside a route file. Every tenant-scoped query carries `eq(table.tenantId, tenantId)` from the auth context — never from the body/query.
- Side effects that may outlive the response (activity writes, realtime nudges, the tracer flush) go through `defer(...)` from `withAuth` (= `c.executionCtx.waitUntil`, awaited inline when there is no ExecutionContext); a detached promise is killed when the response ends. **Inside an SSE stream there is no `defer`**: the request's `db` is already closing in `waitUntil` once `streamSSE` returned the Response, so open `streamDatabase(c)` (`utils/routes/route-helpers.ts`), await every write and `tracer.flush()`, and `close()` it in the stream's `finally` (`chat.ts`).
- Routes enqueue, never run: anything longer than a request is a queue message or a Workflow (D7). Transactional emails are `email.send` jobs (`enqueueJob(c.env.JOBS_QUEUE, …)` inside the service) — except the magic link, which stays inline because a person is waiting on it.
- Realtime (D8): services `nudge(realtime, realtimeEvent('member.changed', tenantId, { id }))`; the route only passes `realtime` through. Emit after the transaction commits.

## Route anatomy

```ts
router.post('/', validate('json', createThingSchema), async c => {
  const { db, tenantId, user, defer } = withAuthAndDb(c) // throws 401 / 403 no_tenant|pending_approval
  guardPermission(c, 'create', 'Thing')
  const [row] = await db.insert(things).values({ ...c.req.valid('json'), tenantId }).returning()
  defer(() => recordActivity(db, { tenantId, userId: user.id, type: 'thing.created', subjectType: 'Thing', subjectId: row.id }))
  return c.json(row, 201)
})
```

`withAuth(c)` is the tenant-free variant (`tenantId: string | null`) for invite accept, pending
invitations, access requests and `/api/admin/*`. Both also return `cfg`, `logger`, `realtime`
(`{ defer, env }` — hand it to a service that nudges) and `tracer` (D32 — the request's span
recorder, or `noopTracer` when no sink exists, for `withAgentTrace` / `traceChatClient`). `requireMultiTenant(cfg)` → 404
`tenancy_mode_single`. `uuidParam(c, 'id')` → 404 for a non-UUID `:id` (never a DB error).
`streamDatabase(c)` → a second `{ db, close }` for the body of an SSE stream.

New endpoint checklist: schema in `packages/shared/src/` → `validate(...)` → auth seam + permission
guard → tenant-scoped query → tests in `tests/api/` → update this file if a new router appears.
